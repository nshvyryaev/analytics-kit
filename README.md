# analytics-kit

Транспорт, приёмник и хранилище продуктовых событий: три части одного пакета,
рассчитанные на игру в вебвью, которая делится сервером с платежами и не может
себе позволить, чтобы сбор статистики уронил покупку.

Зависимостей нет ни одной — ни в браузерной части, ни в серверной. Пакет
запускается кодом, который принимает деньги (`src/server`) и кодом, который
попадает в клиентскую сборку и должен укладываться в жёсткий бюджет байт
(`src/browser`). Внешняя зависимость в обеих ролях — это чужой код на пути к
оплате или лишние килобайты в бандле игры; ни то ни другое не стоит удобства
чужой библиотеки. Все три части используют только то, что даёт сама платформа:
`fetch`/`sendBeacon` в браузере, `node:sqlite`/`node:crypto`/`node:fs` на сервере.

Бюджет байт для `src/browser` считается по минифицированному коду, который
реально попадает в бандл игры, а не по исходнику с комментариями — измерение
исходника целиком даёт число в разы больше и ничего не говорит о реальном
весе. Комментарии в сборку не попадают, и вырезать их ради экономии байт
бюджета смысла не имеет.

## Три части

- **`src/browser`** — транспорт внутри игры. Копит события в очереди,
  отправляет пачками, переживает закрытие вебвью (см. ниже). Экспортирует
  `createClient(options)`.
- **`src/server`** — приёмник, который принимает пачки по HTTP, устанавливает
  личность игрока по подписи площадки и пишет их через `sink`. Экспортирует
  `createReceiver(options)`, а также `anonSubject`/`playerSubject`/`subject` из
  `identity.mjs` и `prune`/`rollup` из `rollup.mjs`.
- **`src/schema.mjs`** — общий словарь событий: имена и форма свойств. Один на
  клиент и сервер: опечатка в имени события иначе тихо заводит новую метрику, а
  необъявленное свойство тихо копится в базе и ничего не значит.

Клиент и сервер связаны только формой тела запроса, не общим модулем событий:
клиент шлёт имена строками, приёмник их проверяет по словарю сам. Так
клиентская сборка не тащит за собой валидатор, которым никогда не пользуется.

## Транспорт (`src/browser`)

```js
import { createClient } from 'analytics-kit/browser';

const client = createClient({
  endpoint: 'https://example.com/v1/collect',
  app: 'word-chain',
  storage: platformStorage, // { get(key), set(key, value) } — как PlatformStorage в игре
});

client.track('pause', { ms: 1200 }); // можно и до start — события до сессии не теряются
await client.start({ anonId, launch, ctx });
client.track('resume', { ms: 300 });

window.addEventListener('pagehide', () => { void client.stop('pagehide'); });
```

Три правила транспорта, из которых растёт всё остальное:

1. **Наружу не бросаем никогда.** Аналитика, уронившая игру, хуже отсутствующей
   — каждая точка входа (`start`, `track`, `flush`, `stop`) обёрнута, ошибки
   молчат.
2. **Неотправленное переживает закрытие.** Вебвью ВКонтакте и Яндекса
   закрываются без предупреждения; без сохранения очереди в `storage` теряется
   хвост каждой сессии — то есть ровно момент выхода из игры. Вместе с очередью
   сохраняется и порядковый номер события: иначе после восстановления счёт
   начнётся заново, и приёмник примет старые номера за повтор уже записанного и
   молча их отбросит.
3. **Отправка внедряется.** Параметр `send(url, body, beacon)` по умолчанию —
   `sendBeacon`/`fetch`, но тесты подставляют свой, иначе транспорт проверяется
   только вручную в браузере.

Флаш происходит по 20 накопленным событиям либо раз в 15000 мс, очередь
ограничена 200 событиями (старые вытесняются новыми). Все три числа — параметры
`flushAt`/`flushMs`/`maxQueue` у `createClient`.

Бюджет размера: `src/browser/client.mjs` держится в 3 КБ после gzip — это
единственный файл транспорта, который попадает в бандл игры.

## Приёмник и интерфейс sink (`src/server`)

`createReceiver({ sink, key, apps, verify })` принимает пачки на `/v1/collect`
(тело `{ s, sent_at, e: [{ q, n, t, p }] }`) и открытие сессии на `/session`
(тело `{ app, anon_id, launch, ctx }`, ответ `{ session_id }`). Хранилище за
приёмником не жёстко зашито — это интерфейс `sink`:

Для событий, о которых знает только сервер (начисление после платёжного
колбэка, отказ по подписи), — `receiver.track(app, name, props, identity?)`.
Без `identity` событие ложится в общую серверную псевдосессию
(`subject_id = 'server'`), как и раньше. С `identity = { platform, playerId }`
— в псевдосессию, привязанную к этому игроку на этот день и
псевдонимизированную той же функцией (`playerSubject`), что и клиентские
сессии: так подневные счётчики в свёртке (`hints_bought` и т.п.) ложатся на
настоящего игрока, а не на фиктивного «server».

```ts
interface Sink {
  session(row): void;
  events(rows): number; // сколько реально записано
  close(): void;
}
```

В пакете два приёмника, оба реализуют этот интерфейс: `createSqliteSink` —
основной, на `node:sqlite`, и `createNdjsonSink` — запасной, строка JSON на
событие. Второй нужен не только для отладки глазами и `jq`: он доказывает, что
интерфейс `sink` не протёк подробностями SQLite, и переезд на другое хранилище
будет заменой одной строки, а не переписыванием приёмника.

### Три слоя базы, три срока жизни

Схема SQLite (`sinks/sqlite.mjs`) состоит из трёх слоёв с разным ретеншеном:

- **Сырьё** (`sessions`, `events`) — необработанные сессии и события. Живёт
  тридцать суток и отсекается функцией `prune`; это тело запросов, а не
  метрика, хранить его вечно не нужно.
- **Измерение** (`subjects`, `aliases`) — кто есть кто: псевдонимы игроков,
  привязка анонимного идентификатора к игроку после входа.
- **Свёртки** (`activity`) — подневные счётчики по игроку, которые строит
  `rollup`.

Измерение и свёртки живут вечно — глубина истории по игроку не должна зависеть
от того, насколько глубоко хранится сырьё. Отдельный файл базы (не общие
таблицы с платежами) — тоже требование этого разделения: перенос статистики на
свой сервер должен стоить переноса файла, а не расплетения таблиц.

## Подключение

```
npm install analytics-kit  # или submodule/vendor — пакет без сборки, чистый ESM
```

```js
import { createReceiver, createSqliteSink, openAnalyticsDb, prune, rollup } from 'analytics-kit/server';
import { createClient } from 'analytics-kit/browser';
```

Спека сбора событий и модель данных, под которую написан этот пакет:
[`docs/acceptance/analytics.md`](../word-chain/docs/acceptance/analytics.md) и
[`docs/analytics-plan.md`](../word-chain/docs/analytics-plan.md) в репозитории
`word-chain`.
